# Security model and release boundary

The academy core also has a verified first hosted deployment (2026-10-16, ADR 0043). Hosted coding/SQL/practical execution remains unavailable pending a separately isolated worker. This release has not completed a production penetration test, public hostile-code acceptance or multi-instance operational hardening.

## Implemented
- Passwords use per-password random salts and scrypt (`N=131072`, `r=8`, `p=1`, 128 MiB work factor); comparisons use constant time. Legacy hashes created during the initial development session are upgraded after successful sign-in.
- Opaque 256-bit random sessions, stored as SHA-256 digests. HttpOnly, SameSite=Lax cookies; expiration and sign-out revocation are checked server-side.
- `SECURE_COOKIES=true` enables Secure cookies for HTTPS deployments. Local HTTP uses false.
- Mutations require a custom `X-Academy-Request: 1` header. Browser Origin values must match `ALLOWED_ORIGINS`. The API does not enable cross-origin credential access.
- Login, registration and password/recovery operations share a bounded, per-process/IP throttle. Do not trust forwarded client headers without a defined proxy trust boundary.
- Every learner-owned operation uses the authenticated user ID. PostgreSQL mutations lock that learner's user row and recheck the session afterward, preventing a queued operation from using a revoked session. Actual PostgreSQL recovery races and this lock/revocation ordering are verified; SQLite does not provide the same row-lock semantics.
- SQLAlchemy parameter binding, Pydantic field limits, strict answer indices and stable content identifiers.
- Database transaction completion occurs before the success response is sent using function-scoped dependencies.
- Personal-plan preferences are learner-scoped; clients cannot choose a user ID. Recommendations use submitted result summaries, never active answers or private snapshot fields.
- Project drafts/history belong to the authenticated owner. An explicit invitation to an already registered account grants access only to that submitted artifact, rubric and feedback. Revoked invitations cannot read or review it. Reviewer identity and self/human classification are derived server-side; clients cannot assign a grade to another account. Submission-row locks serialize review/grant changes in PostgreSQL; PostgreSQL concurrency remains unverified.
- Submitted artifacts and feedback are immutable; rubric snapshots prevent later criteria changes from rewriting history. Evidence has field limits and plain-text rendering. Repository URLs require HTTPS without embedded credentials, and are never fetched by the API. Test commands/output are stored as reported evidence, never executed. Invitations send no email and confer no access to drafts, exams, notes or unrelated learner state.
- Answer keys stay in API-only content. Active assessment responses exclude answers and explanations; submitted results are immutable.
- Exam attempts freeze their definitions and grading policy on the server. Active response fields are allowlisted; tests check that answer keys, explanations and code-validation fixtures cannot leak. Legacy pilot snapshots are backfilled from a frozen migration definition; unknown missing snapshots fail closed.
- Recall sessions are account-scoped and pin private question/key/policy snapshots. Active fields exclude accepted answers, explanations and author validation snippets. Exact grading never executes submitted text. Saved drafts require strict answer/help fields, answers have a 120-character limit and starts are bounded to 20 per ten minutes / 2,000 per account. Submitted results are immutable, and discarded questions stay seen. Independence is self-reported; results are limited evidence and do not grant mastery or access. The browser fixture for delayed checks may age only dedicated test-account practice timestamps and is not an API endpoint. See ADR 0014.
- Lesson checkpoints expose prompts/options before submission, with private keys. Strict indices, versions and UUID keys prevent client-assigned grades and duplicate successful retries. Account-scoped history pins fixed feedback and excludes validation snippets/raw snapshots. Limits are 40 recorded attempts per ten minutes / 4,000 per account. Submitted text never executes; guided work grants no mastery or access. Recorded checkpoints count as study exposure/assistance for recall, not as fresh retention evidence. Native text diagrams/glossary entries execute no scripts. See ADR 0015.
- Markdown is rendered without executing raw HTML or MDX. Notes are plain text fields, not injected HTML.
- Project starter downloads require authentication and use a fixed registry of twenty authored bundles: four six-file bundles (expense tracker, event timeline, typed task inbox and streaming service log), the 13-file installable HTTP ingestion lab, the nine-file policy lab, the eleven-file async feed lab, the seven-file feed-object lab, the eleven-file typed transformation lab, the eight-file resource scopes lab, the nine-file bounded offload lab, the ten-file measured-cache lab, the eleven-file ingestion-persistence lab, the nineteen-file ingestion-service lab, the thirteen-file competing-ingestion extension, the fourteen-file durable-outbox extension, the fourteen-file leased-worker extension, the fifteen-file broker-delivery extension the sixteen-file migration extension and the twelve-file recovery extension. The caller cannot supply a path. Maintainer reference implementations and assessment answer banks are excluded. The API never executes the starter or learner code. The HTTP lab runs locally against trusted configured destinations; its URL syntax rules do not establish SSRF protection or a total deadline. See ADR 0016.
- API responses are no-store. Frontend adds nosniff, frame denial, a referrer policy and a restrictive permissions policy.
- Container application processes run as non-root users. Compose publishes only the frontend to loopback.

## Before public deployment
- Use HTTPS, unique credentials, Secure cookies and explicit public allowed Origins. Replace all local defaults.
- Add ingress request-body/rate limits, shared multi-instance throttling, abuse controls for public registration and a tested proxy trust configuration. Password hashing intentionally consumes memory; hash work now has a per-process two-slot bound, but service/ingress resource limits remain necessary.
- Offline recovery and session/password controls are implemented and verified locally. Add verified email ownership, a reviewed email recovery path if required, shared abuse controls and periodic expired-session cleanup.
- Review assignments currently target normalized registered-account emails; confirm stronger identity and reviewer trust before public use. Existing account creation does not verify email ownership. Reviewer qualifications are not checked.
- Pin/hash all Python dependencies and container images, automate recurring dependency review, and assess a suitable CSP.
- Extend the verified account/session PostgreSQL races and isolated backup/migration drills to broader domain concurrency, actual incident promotion/offsite restore, service resource limits, monitoring, audit logging and hosting rollback.
- Extend content-version pinning beyond exam snapshots before supporting historical curriculum/enrollment migrations.

## Untrusted code and AI
The API never executes learner code. Six Python/SQL exercises use a separate authenticated loopback runner, gated by 13 verified isolation probes. Fresh non-root containers enforce read-only roots, no host mounts/secrets, no network, default seccomp, dropped capabilities, CPU/memory/process/file/time/output limits and cleanup. See [ADR 0013](docs/adr/0013-isolated-coding-and-sql-runner.md) for the exact profile, admission rules and powerful trusted Docker-controller boundary. This is verified local use; hostile public execution requires additional isolation and abuse review. AI grading is not implemented and must never become an authorization boundary. Project checklists are self-reported; they do not certify secure code or raise mastery.

## Everyday access and recovery boundary

Migration c3970b860e75 adds hashed 256-bit offline one-use keys only when an owner acts. Recovery atomically consumes the key and revokes all sessions; password change also revokes the old key. Well-formed failed recovery requests perform the same expensive hash work and use one generic credential error. Keys have no timed expiry before use/revocation; keep them offline. Current-password proof is required for creation/rotation/revocation and password change. No email delivery or automatic administrator reset is provided. Account-owned session identifiers cannot be used to authenticate.

Authenticated exports use public serializers/allowlisted fields, exclude credentials/sessions/raw private definitions/active keys and keep personal Markdown text literal. Exports still contain private notes/source and are not database imports. Trusted maintenance archives **do** include raw private database state: mode 0600, trusted origin, encrypted/offsite storage and retention are operator responsibilities. Restore commands use fresh targets and never overwrite serving data; keep is explicit and successful-only. Revoke restored sessions/keys before actual traffic promotion. Digests are integrity checks, not signatures.

The restricted Compose application role has no superuser/create-database/create-role/replication/bypass-RLS privileges but owns its schema for migrations. Mutation bodies are streamed up to 256 KiB. Readiness fails on database/schema errors; process liveness is separate. The Docker Desktop host bridge is observed locally with private controller authentication and environment proxies disabled; it is not public worker hardening. See [ADR 0042](docs/adr/0042-everyday-recovery-exports-and-isolated-restore.md) and [OPERATIONS](docs/OPERATIONS.md).
