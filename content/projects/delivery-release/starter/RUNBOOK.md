# Local release rehearsal

This runbook operates an installed lab in a disposable schema, on loopback. It is not a deployment procedure for the whole academy. Stop all lab writers, publishers and consumers before changing schema. Confirm which database/schema you own privately. Never paste DSNs or credentials into reports, terminals captured for sharing, source code or Git.

1. Supply explicit ACADEMY_RELEASE_DSN and ACADEMY_RELEASE_TOKENS in private process configuration. Tokens is a JSON object of 1–8 distinct 16–64 ASCII credentials mapped to validated namespaces. DSN has a 1024-character bound; token JSON a 4096-byte bound. No example credentials are defaults. Keep files mode 0600, outside Git. Snapshot configuration once per release; restart to rotate it. This is local environment ownership, not a complete secret rotation service.
2. With all writers/workers stopped, run `python -m academy_delivery_release.operate prepare`, then `python -m academy_delivery_release.operate check`. Prepare explicitly upgrades/checks the installed combined migration metadata. Check requires delivery_004 plus the required table/column query shapes and a separate autogenerate comparison. Neither command repairs CHECK expressions or validates every existing data row. A migration failure must stop the release; do not stamp a revision or retry blindly.
3. Run `python -m academy_delivery_release.operate serve --port 8011`. It binds 127.0.0.1 only. Startup requires a fresh readiness observation, then admits requests. /health means the process can answer; /ready also observes this API's PostgreSQL dependency. Neither establishes authorization or guarantees the next transaction will succeed. Redis is a worker dependency, checked separately by the recovery demo; API readiness does not imply broker health.
4. Observe /health 200 and /ready 200; observe unauthenticated business 401, wrong-namespace 403 and configured-namespace 200. Do not log Authorization. Public readiness contains only finite reasons: ready, schema-head, schema-contract, storage-unavailable, stopping. Required-column probes use LIMIT 0 and a read-only transaction with 250ms lock/1000ms statement limits. Connection acquisition/individual SQL bounds are not a hard HTTP deadline. Program errors are not converted into ready status.
5. Diagnose finite JSON lifecycle events startup-ready/startup-refused/stopping/disposed and operation-refused. Existing business request signals carry trace/status. No raw database exception, token or DSN belongs in public output. These are finite signals, not a full metrics/tracing/alerting system. If /health works and /ready fails, inspect head/schema/storage privately. An observed ready result is temporary; business writes still own permission and commit checks.
6. Send SIGTERM to the process you started, wait/reap it, then confirm its tagged database connections are gone. Uvicorn stops admission and waits for cooperative work with a configured three-second graceful budget. A stuck synchronous callback may exceed that budget; this lab does not prove a hard kill deadline. The in-process release.stop flag rejects subsequent business requests and readiness but does not cancel previously admitted work. It has no public mutation endpoint. Only after shutdown may migration/rollback proceed.
7. Decide retained and lost data BEFORE rollback. delivery_003 retains service facts/timestamps, outbox/inbox/effects but deletes worker_policy/delivery_job (attempt budgets, generations, deadlines and job status). service_002 also deletes outbox/inbox/effects: prior receipt/deduplication history is lost while service facts/timestamps remain. Broker payloads are independent and unchanged. Losing inbox history permits the same Event to apply again after re-upgrade. Stop replay until a separate recovery decision is made. Neither binary rollback nor schema rollback is backup restoration.
8. Run `python -m academy_delivery_release.operate rollback --target delivery_003 --allow-loss` only after accepting that concrete loss. The CLI refuses unnamed targets and absent loss flags before connecting. Replace the target with service_002 only if you accept its larger loss. New compatible startup must now refuse the old head. Rolling back only the binary leaves the old service's readiness failing at delivery_004.
9. Explicitly prepare/check again before restarting. Re-upgrade creates empty lost history; it does not recover budgets or receipts. Save the actual head, HTTP statuses, owned process exit, retained/lost row evidence and cleanup in your artifact. The supplied demo changes a revision in an owned fixture solely to observe readiness transitions; never copy that fault into a real operation. Use actual installed TCP tests and report any skips.

Review: explain why a stopped schema change is required here; name the head/columns/read-only scope; show failed startup and normal shutdown both dispose once; distinguish observation from guarantees. PostgreSQL stays running during child shutdown. There is no zero-downtime rollout, backup/restore, hostile code isolation, broker failover or full academy Compose claim.
