# Delivery schema lab

Keep existing service facts while adding versioned delivery tables. Implement upgrade, downgrade and check in operations.py. The supplied metadata, guarded connection owner and immutable revision resources support your work. The academy does not execute this project or award mastery for your checklist/reported tests.

## Install the completed dependencies first
Build and install the completed service, competition, outbox, leased-worker and stream-delivery wheels in a fresh Python 3.13+ environment. Then `python -m pip install '.[dev]'`. Distribution academy-delivery-schema-lab 0.1.0 imports as academy_delivery_schema. Do not use an unfinished dependency wheel. Run `python -m pytest`, `python -m mypy --strict src demo.py`, `python -m ruff check src tests demo.py` and `python -m build`. An outside-source installed run must resolve actual packaged migrations/py.typed and actual distribution versions.

## Exact contract
- upgrade(engine, revision="head") accepts only exact strings service_002, delivery_003, delivery_004 or head. Fresh schemas and existing service_002 schemas work. The chain contains unchanged service_001/002, then delivery_003 outbox/inbox/effect and delivery_004 policy/job/index. No stamp, create_all, implicit backfill or old one-time DDL adoption. A repeated head upgrade is a no-op, not a drift check.
- downgrade(engine, revision, allow_loss=False) permits only service_002/delivery_003 and exact bool True before acquiring a connection. Base/service_001 are refused by this public wrapper. Removing worker tables loses leases/policy history; removing outbox/inbox/effect loses delivery and deduplication history. The service key/value/ingested_at rows remain. A retained broker can replay after inbox deletion; this flag is not proof rollback is operationally safe.
- check(engine) requires exactly delivery_004, then Alembic's combined autogenerate check with type/server-default comparison. inspect_state(engine).at_head checks revision only. Autogenerate detects many table/column/index/FK/default differences, but does not establish CHECK expression validity, data invariants or runtime compatibility. The live suite demonstrates this blind spot explicitly.
- Use the supplied migration(engine) guard: PostgreSQL READ COMMITTED, one owned transaction/connection, transaction-local lock_timeout 250ms/statement_timeout 5000ms, database-wide cooperating advisory lock. BusyMigration fails immediately. Exception propagates after rollback/release; no automatic retry. The caller owns configured engine/search_path/disposal. The advisory lock does not stop writers, administrators or other migration tools; pause all producers/consumers/writers before schema change. Per-statement limits are not a total migration deadline.
- The previous service business routes retain their permission/output contract. Its old /ready expects service_002 and returns 503 at the new delivery head: release coordination must use the explicit new inspect_state/check workflow and a compatible application. Old install() helpers must not be called after versioned upgrade. No SQL migration changes Redis keys or trims payloads.

## Rehearse only in an explicitly disposable database
The tests create unique schemas in ACADEMY_SCHEMA_DSN and drop only those schemas. Missing PostgreSQL explicitly skips live checks. Broker integration additionally needs private ACADEMY_BROKER_URL; it removes only its generated stream key. Never point these variables at the academy database or production. The maintainer helper provides owned digest-pinned PostgreSQL/Redis with private temporary credentials; the academy never supplies credentials to learner code.

Run `python demo.py --output schema-evidence.json` with both private store settings. It preserves actual timestamped old facts through upgrade, checks combined drift, composes real broker delivery, observes explicit destructive downgrade, re-upgrades with empty history, and records installed versions/previous API status. Reports are evidence, not certification. Add regressions for late failed upgrade/downgrade, actual DDL lock contention, head-only false confidence and cleanup.

## Review your result
Show old facts before/after each revision, exact revision and separate drift result, actual SQL rollback and lock evidence, engine release, installed resources and lost history. Explain why writers must be paused, legacy setup is rejected, old readiness fails and dropping the inbox can repeat an effect. This is a finite migration rehearsal, not zero-downtime deployment, a backup restoration, power-loss recovery or full production readiness.
